# 013: private Copilot conversation history and inert review plans

This is an explicit operator migration. It is not run by Control startup and
makes no provider calls, source fetches, backfills, credentials or execution jobs.
Use the existing documented schema-migration command with the intended database.

## Before migration

1. Back up the database and test restore. Retain the old application and schema.
2. Stop Control writers during DDL. MySQL DDL implicitly commits; this migration
   does not claim atomic DDL or mixed-version rollout compatibility.
3. Leave `copilot.history.enabled` false. Configure the existing managed 32-byte
   `ARCENTRA_SECRET_ENCRYPTION_KEY` only through the established secure operator
   process. No key is generated by this feature. Keep that key for restored data.
4. Verify the selected database, expected schema version, free space and privileges.
   Run `MigrateSchema` through the existing explicit CLI. No legacy content is read
   to infer a conversation or create request. A partial history schema or duplicate
   database-comparison identities fails preflight before any DDL.

## Added tables and guarantees

`copilot_conversation`, `copilot_turn`, `copilot_action_plan` are new tables.
Existing run, pipeline, user, secret and provider records are unchanged. Reapplying
an intact schema is idempotent. Application code never accepts ambiguous or
case-aliased IDs returned by a case-insensitive collation. Unique indexes are
required on conversation IDs, turn IDs, plan IDs, per-owner/project request keys,
and conversation sequence. Request conflicts fail closed rather than upsert.

Only fixed identifiers, typed states, timestamps and opaque bindings are readable
columns. Body and patch fields accept bounded ciphertext; crypto/authenticated
additional-data validation and redaction belong to the service layer. Repository
SQL logging is disabled and raw driver errors are not returned.

Body retention is 30 days from each body's creation; a conversation expiry tracks
its latest body without extending older turn expiries. Plan eligibility and plan
ciphertext expire within 24 hours and never outlive the parent turn. Reads exclude
expired content before cleanup. Explicit deletion immediately wipes turn/plan
ciphertext and fences workers in one bounded transaction. A conversation admits
at most 200 turns (including pre-cancel tombstones) and 100 plans. Owner-wide
admission permits at most two active turns, serialized on the current exact user
row across instances and projects. There are also 1,000-conversation and
20,000-turn owner capacity bounds; reaching a bound fails before transmission.

Request metadata remains through the later of parent lifetime and 90 days after
request creation. Parent metadata remains through all child request horizons.
Expiry cleanup uses indexed content-present/expiry pages; erased rows cannot
starve later bodies. Each purge invocation accepts 1–200 work items; removing a
fully expired parent can remove its bounded 200-turn/100-plan metadata children.
No plaintext recovery log is created. Backups follow operator backup retention;
deleting online ciphertext does not claim immediate backup erasure.

The service must pass a fresh live authorization callback to every user read and
write. Repository lock order is pipeline, project, pinned immutable run, exact
actor/current authorization, conversation, turn/plan. Grant expiry is checked
again before commit. Do not hold locks across provider/SCM HTTP. Responses still
have an unavoidable interval between final authorization and network delivery;
already delivered data cannot be recalled. Maintenance never takes domain locks
while holding history locks, never dispatches providers and never replays consent.

`reserved` lease expiry becomes `interrupted`; `dispatching` expiry becomes
`outcome_unknown`. The latter says only that the provider may have received data.
An explicit new attempt requires a new request key and fresh preview/consent.
A completed finalization with a lost acknowledgement is reconciled by primary
request read, never an upstream retry. No action executor or fourth ledger exists.

## Verification and rollback

Run the focused SQLite suite and the opt-in disposable real-MySQL suite. Required
mode is `ARCENTRA_REQUIRE_COPILOT_HISTORY_MYSQL=1`; the explicit connection is
`ARCENTRA_COPILOT_HISTORY_MYSQL_DSN`, restricted to a dedicated
`arcentra_copilot_history_test` (or suffixed) schema. The test refuses nonempty
schemas. It tests binary and supported case-insensitive collations. Missing
infrastructure fails required mode; a skipped opt-in suite is not MySQL acceptance.

Disable history before application rollback. Do not drop new tables to roll back
code: preserve encrypted history/tombstones and the managed key. Restoring a prior
backup loses post-backup idempotency state; do not resume or replay prior provider
requests. An incomplete DDL application requires inspection and restoration or an
explicitly reviewed repair, not automated inference. Key rotation must account for
history AAD and ciphertext via the existing operator-controlled maintenance plan.
